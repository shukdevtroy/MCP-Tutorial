2What Is This Project?

↑ Contents

This project is a Personal Knowledge Base Chatbot. It lets a user chat, in plain English, with their own collection of personal Markdown notes. Instead of manually searching files, the user simply asks a question, and the chatbot finds the right notes and answers using them.

In This Project — The knowledge base is a folder called notes/ containing four real Markdown files:
  • meeting_notes_2026-09-10.md — decisions and action items from a work meeting
  • project_ideas.md — a list of software project ideas, including this very chatbot ("Project Nightjar")
  • recipe_notebook.md — a cooking recipe with ingredients and notes
  • travel_plans.md — notes about an upcoming trip

Why isn't an LLM alone enough?

A plain LLM only knows what it was trained on. It has never seen this user's personal notes, and it cannot browse the user's computer by itself. If you asked a plain LLM "what did we decide about the cache?", it could only guess — and guessing about someone's private life or work decisions is exactly the kind of "making things up" (hallucination) that makes chatbots unreliable.

Why are tools required?

To answer correctly, the LLM needs a way to reach out and read real data. A "tool" is simply a function the LLM is allowed to call — for example, "search my notes for X." The LLM decides when to call a tool and what to search for; the actual searching is done by ordinary Python code, not by the LLM's imagination.

Why MCP specifically?

MCP (Model Context Protocol) is simply a standard, agreed-upon way for an AI application to talk to a tool provider. Instead of writing one-off, custom glue code for every project, this project uses MCP so that the "tool provider" (the note-search service) is a separate, swappable, standardized component.

Why store notes as Markdown?

Markdown files are plain text, human-readable, easy to edit in any text editor, and require no database setup. That makes them a natural fit for a lightweight personal knowledge base that a single student or hobbyist can maintain by hand.

Key Takeaway — This project is not a general-purpose chatbot. It is a chatbot deliberately restricted to answering from the user's own notes, using tools to fetch real content instead of guessing.

Explaining every arrow

  • User → Gradio UI: the user types a message into the chat box built with gr.ChatInterface.
  • Gradio UI → run_tool_calling_loop(): Gradio calls chat_fn(), which builds a list of OpenAI-style messages and hands them to the tool-calling loop.
  • run_tool_calling_loop() → OpenRouter: the loop sends the conversation, plus the schema of the discovered MCP tools, to OpenRouter over a normal HTTPS request via call_openrouter().
  • run_tool_calling_loop() → mcp_server.py: when the LLM's reply contains a tool call, the client sends that call to the already-running mcp_server.py subprocess over stdio (standard input/output), using the MCP ClientSession.
  • mcp_server.py → tools: the server routes the request to the matching Python function — search_notes, read_note, or reindex_notes.
  • tools → notes/*.md: search_notes and read_note read from _notes_cache, which is loaded from the Markdown files.
  • tools → TF-IDF engine: search_notes converts the query and the notes into numeric vectors and ranks them by cosine_similarity.
  • Result flows back up the same path: server → client → appended as a "role": "tool" message → sent back to OpenRouter → the LLM writes the final natural-language answer → Gradio displays it.
Student Tip — Notice there are two separate network-style connections: an HTTPS call to OpenRouter (for the LLM's "thinking"), and a stdio pipe to the local mcp_server.py subprocess (for "doing"). Keeping these separate is central to the whole MCP idea.

4What Is an LLM? (and OpenRouter's Role)

↑ Contents

LLM basics

A Large Language Model (LLM) is a program trained on huge amounts of text that has learned statistical patterns of language well enough to generate coherent, relevant text in response to an input.

  • Prompt — the text you send the model, including instructions and context.
  • Context — everything the model can "see" at once: system instructions, chat history, and tool results.
  • Token — a chunk of text (roughly a word or part of a word) that the model reads and generates one piece at a time.
  • Response — the text (or structured tool call) the model produces.

Why can't an LLM access local files by itself?

An LLM is just a text-in, text-out function running on a remote server. It has no hands, no file system access, and no memory of this specific user's computer. The only way it can "see" the user's notes is if something else — the MCP client and server — fetches the content and hands it to the model as plain text inside the conversation.

OpenRouter's role in this project

OpenRouter is a hosted gateway that lets a program send chat requests to many different LLMs through one consistent API, without the project needing to manage its own GPU servers. In this project, OpenRouter is the "phone line" the client uses to reach the LLM.

In This Project — 
OPENROUTER_URL = "https://openrouter.ai/api/v1/chat/completions"
MODEL_NAME = os.environ.get("KB_MODEL", "stealth/union-alpha")
OPENROUTER_URL is the single HTTP endpoint used for every LLM call. MODEL_NAME picks which model OpenRouter should route the request to; it defaults to a specific model name but can be overridden with the KB_MODEL environment variable. The code comments note that not every free OpenRouter model reliably supports tool calling, so this choice matters.

Now let's look at the actual function that talks to OpenRouter:

def call_openrouter(messages, api_key):
    if not api_key:
        raise RuntimeError("Enter your OpenRouter API key in the box above first.")
    resp = requests.post(
        OPENROUTER_URL,
        headers={"Authorization": f"Bearer {api_key}", "Content-Type": "application/json"},
        data=json.dumps({
            "model": MODEL_NAME,
            "messages": messages,
            "tools": _mcp_tools_schema,
        }),
        timeout=60,
    )
    resp.raise_for_status()
    return resp.json()

Line by line, in plain language:

  • if not api_key: raise RuntimeError(...) — refuses to call OpenRouter without a key, and tells the user exactly what to do.
  • requests.post(OPENROUTER_URL, ...) — sends an HTTPS POST request, the standard way to talk to a REST API.
  • headers={"Authorization": f"Bearer {api_key}", ...} — proves who is calling, using the key the user typed into the Gradio textbox.
  • "model": MODEL_NAME — tells OpenRouter which underlying LLM to route the request to.
  • "messages": messages — the entire conversation so far (system prompt, user turns, assistant turns, and any tool results).
  • "tools": _mcp_tools_schema — the list of tools the LLM is allowed to call, discovered from the MCP server (explained fully in Chapter 8). This single line is what makes tool calling possible: without it, the model has no idea search_notes exists.
  • resp.raise_for_status() — turns any HTTP error status into a Python exception, so failures aren't silently ignored.
Key Takeaway — OpenRouter never touches the notes directly. It only ever sees the conversation text and the tool schema — the actual file reading happens entirely inside mcp_server.py, on the user's own machine.

5What Is MCP?

↑ Contents

MCP stands for Model Context Protocol. It is a standardized way for an AI application (like an LLM-powered chatbot) to connect to external tools and data sources.

The problem MCP solves

Before standards like MCP, every project that wanted an LLM to use "tools" had to invent its own custom wiring: its own way of describing tools, its own way of calling them, its own way of returning results. That made tools hard to reuse across projects. MCP fixes this by defining one common protocol: any MCP-compatible client can talk to any MCP-compatible server, regardless of who wrote either side.

Core MCP vocabulary

  • MCP Server — a small program that exposes a set of "tools" (and optionally other resources) following the MCP specification.
  • MCP Client — the program that connects to an MCP server, asks what tools are available, and calls them on behalf of the AI application.
  • MCP Tool — a single callable capability, with a name, a description, and a defined set of input parameters.
  • MCP Protocol — the message format and rules both sides follow so they always understand each other, regardless of implementation language.
  • stdio transport — one way for the client and server to exchange MCP messages: by writing to and reading from each other's standard input/output streams, typically because the server runs as a local subprocess.
Simple Example — Think of MCP like a restaurant menu format that every restaurant in a city agrees to use. A delivery app (the "client") doesn't need custom code for every single restaurant ("server") — it just reads each restaurant's menu in the same standard format and places orders the same standard way.
In This Project — mcp_server.py is the MCP server; it exposes three tools. kb_assistant_mcp.py is the MCP client; it connects to that server over stdio, because the server is launched as a local subprocess on the same machine rather than reached over a network.

↑ Contents

Beginners very often mix up "client" and "server." This table should make the distinction permanent.

Student Tip — A simple rule of thumb: the server owns the data and the logic (it knows how to search notes); the client owns the conversation (it knows how to talk to the user and the LLM, and it asks the server to do work on its behalf). In this project the client and server run on the same laptop, but MCP is designed so a server could just as easily run on a completely different machine.

Setting up FastMCP

from mcp.server.fastmcp import FastMCP
mcp = FastMCP("kb-notes")

FastMCP is a helper class from the official MCP Python SDK that takes care of the MCP protocol details — message formatting, the stdio transport loop, and advertising tools to a connecting client — so the project author only has to write ordinary Python functions and mark them as tools. FastMCP("kb-notes") creates a server instance and gives it the name "kb-notes".

The three tools

search_notes(query, top_k)

@mcp.tool()
def search_notes(query: str, top_k: int = 3) -> str:
    """Search the user's personal notes and return the most relevant snippets."""
    ...
    query_vec = _vectorizer.transform([query])
    scores = cosine_similarity(query_vec, _doc_matrix).flatten()
    ranked = sorted(zip(_filenames, scores), key=lambda x: x[1], reverse=True)
    ...

  • Purpose: find which notes are most relevant to a question.
  • Input: query (the search text) and top_k (how many results to return, defaulting to 3).
  • How it works: the query is turned into a TF-IDF vector, compared against every note's vector using cosine similarity, and the notes are sorted best-match first.
  • Output: a JSON string — a list of objects, each with filename, a rounded relevance_score, and a 500-character snippet of the note. Notes scoring 0 (no overlap at all) are skipped, and if nothing scores above 0, the tool returns an informational message instead of an empty list.

read_note(filename)

@mcp.tool()
def read_note(filename: str) -> str:
    """Read the full content of one specific note by its exact filename."""
    content = _notes_cache.get(filename)
    if content is None:
        return json.dumps({"error": f"Note '{filename}' not found. ..."})
    return json.dumps({"filename": filename, "content": content})
  • Why it exists: search_notes only returns short 500-character snippets to keep results compact. If the LLM needs the full content of one specific note, it calls read_note with the exact filename returned by search_notes.
  • What happens if the file doesn't exist: the function returns a JSON error object explaining the note wasn't found, rather than raising an exception that would crash the tool call.

reindex_notes()

@mcp.tool()
def reindex_notes() -> str:
    """Re-scan NOTES_DIR and rebuild the search index (call after adding/editing notes)."""
    build_index()
    return json.dumps({"status": "ok", "notes_indexed": len(_filenames)})
  • Why an index needs rebuilding: the TF-IDF index is a snapshot computed once (when the server starts). If notes are added or changed on disk afterward, the snapshot goes stale — new content won't be searchable until the index is rebuilt.
  • What it does: simply calls build_index() again, which reloads every Markdown file from disk and recomputes the TF-IDF vectors, then reports how many notes are now indexed.
Key Takeaway — All three tools return strings containing JSON, not raw JSON objects. This matters because MCP tool results, and the OpenAI-style "tool" messages that carry them, are transmitted as text.

8Tool Discovery: How the LLM Learns What Tools Exist

↑ Contents

What a decorator is

In Python, a decorator is a piece of syntax (@something) placed above a function that wraps or registers that function with extra behavior, without you having to rewrite the function itself.

@mcp.tool()
def search_notes(query: str, top_k: int = 3) -> str:
    """Search the user's personal notes and return the most relevant snippets.

    Args:
        query: search text
        top_k: number of results to return (default 3)
    """

@mcp.tool() tells the FastMCP instance: "register this ordinary Python function as an MCP tool." Behind the scenes, FastMCP reads the function's name, its docstring (used as the tool description), and its type-hinted parameters (used to build the tool's input schema) — turning a plain Python function into something an MCP client can discover and call remotely.

The client asking "what tools exist?"

tools_result = await session.list_tools()

Instead of the client author manually typing out a list of tool names and parameters (which would break the moment the server changes), the client asks the server directly, at connection time, "what tools do you have?" This is tool discovery. The server answers with the live list of everything currently decorated with @mcp.tool() — including each tool's name, description, and parameter schema.

Converting MCP tools into an OpenAI-style schema

def _mcp_tools_to_openai_schema(tools):
    schema = []
    for t in tools:
        schema.append({
            "type": "function",
            "function": {
                "name": t.name,
                "description": t.description or "",
                "parameters": t.inputSchema,
            },
        })
    return schema

MCP describes tools its own way, but OpenRouter (like the OpenAI API it mirrors) expects tools described in a specific JSON shape called the tools / function-calling schema. This function is a translator: for every MCP tool discovered, it builds a matching entry with type: "function", the tool's name, description, and parameter schema — producing exactly the list that later gets attached as "tools": _mcp_tools_schema inside call_openrouter().

Key Takeaway — The LLM never reads Python source code. It only ever sees the name/description/parameter schema produced by this discovery-and-translation chain — which is exactly why writing a clear docstring on a tool function matters: that docstring is literally what tells the LLM when and how to use the tool.

9The MCP Client: kb_assistant_mcp.py

↑ Contents

The client's job is to launch the server, keep a connection open, discover its tools, and relay tool calls back and forth. Four building blocks from the official mcp SDK make this possible.

Building BlockRole
StdioServerParametersDescribes how to launch the server subprocess — which command and arguments to run.
stdio_client(...)Actually starts that subprocess and gives back a readable/writable pair of streams connected to its stdin/stdout.
ClientSessionWraps those raw streams with the MCP protocol logic: sending requests, receiving responses, and matching them up.
AsyncExitStackA standard Python tool for safely managing several "context managers" (things that need clean setup and teardown) together, so the subprocess and session are properly closed if anything goes wrong.

Launching the server as a subprocess

server_params = StdioServerParameters(
    command="python",
    args=[SERVER_SCRIPT]
)
In This Project — This tells the client: run the command python mcp_server.py (where SERVER_SCRIPT is the full path to that file) as a brand-new child process. Once started, the client does not talk to it over the network — it talks to it by writing MCP-protocol messages to that subprocess's standard input, and reading its replies from standard output. This is exactly what "stdio transport" means in practice: the operating system's own input/output pipes become the communication channel between two programs running side by side.

The connection sequence

stack = AsyncExitStack()
read, write = await stack.enter_async_context(stdio_client(server_params))
session = await stack.enter_async_context(ClientSession(read, write))
await session.initialize()
tools_result = await session.list_tools()

In order: start the subprocess and get its stdio streams; wrap those streams in a ClientSession; perform the MCP handshake with initialize(); then ask the server what tools it has, storing the answer (converted to OpenAI-style schema, see Chapter 8) for later use by every OpenRouter request.

10The Async Architecture (Why a Background Event Loop?)

↑ Contents

The problem being solved

The MCP client library is asynchronous — its functions are written with async/await and must run inside an asyncio event loop. But Gradio's callback functions are synchronous — plain, ordinary functions that Gradio calls directly and expects a normal return value from. This is a mismatch: synchronous code cannot simply call await on an async function.

The project's solution

_loop = asyncio.new_event_loop()

def _run_loop():
    asyncio.set_event_loop(_loop)
    _loop.run_forever()

threading.Thread(target=_run_loop, daemon=True).start()

The project creates one dedicated asyncio event loop, and runs it forever inside a separate background thread (a daemon thread, meaning it won't block the program from exiting). This loop lives for the entire lifetime of the app and owns the one persistent connection to the MCP server.

fut = asyncio.run_coroutine_threadsafe(_connect(), _loop)
fut.result(timeout=30)

asyncio.run_coroutine_threadsafe() is the bridge: it safely schedules an async coroutine (like _connect() or a tool call) to run on that background loop, from the synchronous Gradio callback thread, and lets the synchronous code wait for the result with .result(timeout=...).

   Gradio callback (synchronous)
              │
              ▼
   Synchronous Python function  (chat_fn, run_tool_calling_loop)
              │  asyncio.run_coroutine_threadsafe(...)
              ▼
   Background asyncio event loop   (running forever in a daemon thread)
              │
              ▼
   MCP async ClientSession   (await session.call_tool(...))
              │  stdio
              ▼
   mcp_server.py  (subprocess)
Key Takeaway — This pattern — one background event loop in its own thread, bridged with run_coroutine_threadsafe — is a common way to use an async library from inside a synchronous framework like Gradio, without rewriting the whole application as async.

12The System Prompt and Grounded Generation

↑ Contents 
SYSTEM_PROMPT = (
    "You are a helpful assistant that answers questions using ONLY the "
    "user's personal notes. Always use the search_notes tool first to find "
    "relevant notes before answering. If you need more detail from a "
    "specific note, use read_note. If the notes don't contain the answer, "
    "say so honestly instead of making things up. Cite the note filename "
    "when you use information from it."
)

The system prompt is the very first message in every conversation, and it sets the ground rules the model is expected to follow for the entire session. Breaking it down:

  • "using ONLY the user's personal notes" — restricts the model's answers to the knowledge base, rather than its own general training knowledge.
  • "Always use the search_notes tool first" — pushes the model toward searching before answering, instead of guessing.
  • "use read_note" for more detail — tells the model there's a second tool for fetching full content once a relevant file is known.
  • "say so honestly instead of making things up" — directly discourages hallucination when the notes simply don't cover the question.
  • "Cite the note filename" — makes answers verifiable; a student or user can go check the exact source file.

Grounded generation, in simple language

Grounded generation means an LLM's answer is tied to (grounded in) real retrieved evidence, rather than produced purely from the model's internal training. Here, the "grounding evidence" is whatever search_notes and read_note return. The system prompt is the main mechanism nudging the model to behave this way — though it is an instruction, not a hard guarantee, since the model could still ignore it.

Student Tip — This pattern — retrieve relevant text, then generate an answer from it — is closely related to what the industry calls RAG (Retrieval-Augmented Generation), except here the "retrieval" is implemented as an MCP tool the LLM actively chooses to call, rather than something automatically run before every message.

13What Is TF-IDF?

↑ Contents

mcp_server.py does not use an LLM to search the notes at all — it uses a classic, purely statistical text-search technique called TF-IDF, short for Term Frequency – Inverse Document Frequency.

from sklearn.feature_extraction.text import TfidfVectorizer
_vectorizer = TfidfVectorizer(stop_words="english")
_doc_matrix = _vectorizer.fit_transform(corpus)

Term Frequency (TF)

TF simply counts how often a word appears in one document. If the word "cardamom" appears three times in the recipe note, "cardamom" has a high term frequency for that note.

Inverse Document Frequency (IDF)

IDF measures how rare a word is across all documents. A word that appears in almost every note (like "the," "and," or "notes") is common and not very useful for telling documents apart, so it gets a low IDF weight. A word that appears in only one or two notes (like "cardamom" or "Bandarban") is distinctive, so it gets a high IDF weight.

Putting them together

TF-IDF score for a word in a document = (how often it appears in that document) × (how rare it is across all documents). Multiplying these means a word only scores highly if it is both frequent in that specific note and uncommon elsewhere — exactly the words that best characterize what makes that note distinct.

Simple Example — Across the four notes in this project, the word "notes" might appear in every file and gets almost no weight. But the word "Bandarban" appears only in travel_plans.md — TF-IDF gives it a high weight there, making that note easy to find when someone searches for "Bandarban."

stop_words="english" tells scikit-learn to automatically ignore extremely common English filler words (like "the," "is," "and") before even computing TF-IDF, since they carry almost no distinguishing meaning.

From words to vectors

Once every word in every document has a TF-IDF score, each document becomes a long list of numbers — one number per unique word in the whole collection. This list of numbers is called a vector. _doc_matrix is simply a table holding one such vector per note. A search query goes through the exact same transformation via _vectorizer.transform([query]), becoming a vector in that same "word-space," so it can be directly compared to the notes (Chapter 14).

Key Takeaway — TF-IDF turns text into numbers based purely on word overlap and rarity. It does not understand meaning or synonyms — searching "kitchen dish" would not automatically match "recipe" unless that exact word also appears in the note. This is an important limitation, revisited in Chapter 26.

14What Is Cosine Similarity?

↑ Contents 
from sklearn.metrics.pairwise import cosine_similarity
scores = cosine_similarity(query_vec, _doc_matrix).flatten()

Once the query and every note are represented as TF-IDF vectors, the project needs a way to measure how "close" the query vector is to each note vector. Cosine similarity measures the angle between two vectors, rather than their raw distance.

Simple Visual Example — Picture two arrows drawn from the same starting point. If they point in almost exactly the same direction, the angle between them is small, and cosine similarity is close to 1 (very similar). If they point in completely unrelated directions, the angle is large and cosine similarity is close to 0 (unrelated). In text search, "pointing the same direction" roughly means "using the same important words in similar proportions."

Why use the angle rather than a simple count of shared words? Because it naturally accounts for document length — a long note and a short note can still score highly similar to a short query if they emphasize the same distinctive words, since cosine similarity normalizes for magnitude.

How the project uses the scores

ranked = sorted(zip(_filenames, scores), key=lambda x: x[1], reverse=True)
...
for filename, score in ranked[:top_k]:
    if score <= 0:
        continue
    ...

Every note gets one similarity score against the query, the notes are sorted highest-score-first, and only the top top_k (default 3) are kept — with any note scoring exactly 0 (no meaningful overlap at all) skipped entirely.

Key Takeaway — A score near 1 means "this note strongly shares distinctive words with the query." A score near 0 means "essentially no shared distinctive vocabulary." The relevance_score field returned by search_notes is exactly this number, rounded to three decimal places.

Why Markdown

Markdown is plain text with light formatting (headings, bold text, lists), which makes it easy for a human to write and edit in any text editor, and just as easy for a program to read as ordinary text — no special parser is required for this project, since the notes are searched and displayed as raw text, formatting characters included.

How files are discovered and loaded

NOTES_DIR = os.environ.get("NOTES_DIR", os.path.join(os.path.dirname(__file__), "notes"))

def load_notes():
    global _notes_cache
    _notes_cache = {}
    os.makedirs(NOTES_DIR, exist_ok=True)
    paths = glob.glob(os.path.join(NOTES_DIR, "**", "*.md"), recursive=True)
    for path in paths:
        with open(path, "r", encoding="utf-8") as f:
            _notes_cache[os.path.relpath(path, NOTES_DIR)] = f.read()
  • NOTES_DIR defaults to a notes folder next to mcp_server.py, but can be overridden with an environment variable — useful if a student wants to point the assistant at a different notes folder.
  • glob.glob(..., "**", "*.md", recursive=True) finds every file ending in .md inside NOTES_DIR, including in subfolders, since ** matches any depth of nested directories.
  • Each file is opened and its full text is stored in _notes_cache, keyed by its filename relative to NOTES_DIR (e.g. "recipe_notebook.md").
  • If a specific file can't be read (permissions, encoding issues, etc.), the error is caught and printed as a warning rather than crashing the whole server.

How the search index is built on top

def build_index():
    global _vectorizer, _doc_matrix, _filenames
    load_notes()
    _filenames = list(_notes_cache.keys())
    if not _filenames:
        _vectorizer = None
        _doc_matrix = None
        return
    corpus = [_notes_cache[f] for f in _filenames]
    _vectorizer = TfidfVectorizer(stop_words="english")
    _doc_matrix = _vectorizer.fit_transform(corpus)

build_index()

build_index() first reloads every note from disk via load_notes(), then fits a fresh TF-IDF vectorizer across the full collection (the "corpus"). This function runs once automatically the moment the server module is imported (build_index() is called at the bottom of the file, outside any function), so the index is ready as soon as the server starts.

17Error Handling in This Project

↑ Contents
SituationHow the Code Handles It
Missing/unreadable note file during loadload_notes() catches the exception per-file and prints a warning, so one bad file doesn't stop the rest from loading.
No notes indexed yetsearch_notes returns a JSON error message telling the user to add .md files, instead of crashing on a missing vectorizer.

A specific tool call fails at runtimeThe exception is caught and turned into a JSON error object that is fed back to the LLM as the tool's result, so the model can adapt its next answer instead of the whole request crashing.
Too many tool-calling roundsMAX_TOOL_ITERATIONS = 5 caps the loop; if exceeded, a friendly "try rephrasing" message is returned.

Why limit tool iterations?

Without a cap, a model could theoretically keep calling tools back and forth indefinitely — burning time, API cost, and never producing a final answer. Capping at 5 rounds protects against this "infinite tool loop" scenario while still giving the model several chances to search and re-search before giving up.

Key Takeaway — Almost every error path in this project returns a readable message instead of letting the program crash silently — a pattern worth copying in your own projects.

19API Keys and Security

↑ Contents

The OpenRouter API key is entered by the user directly into the Gradio textbox at the start of each session and is kept only in the browser form field and in the in-memory messages/function calls for that session — the code never writes it to disk or logs it.

Why not hard-code an API key in source code?

  • Source code is often shared, committed to version control, or copied between machines — a hard-coded key would leak with it.
  • Anyone with read access to the file gets full use of the key (and whatever it's billed for).
  • Keys need to be rotated (replaced) periodically for security; hard-coding makes that painful, since every copy of the code would need updating.
API Key
A secret string used to authenticate requests to an API, proving who is calling and (often) what they're allowed to use or be billed for.
Secret
Any piece of sensitive information (like a password or key) that should not be exposed to unauthorized people.
Environment Variable
A value set outside the source code, in the operating system or shell, that a program can read at runtime — one common alternative to typing a key into a UI each session.
Memory-Only Credentials
A secret that is only ever held in a running program's memory and never saved to a file, so it disappears the moment the program stops.
.gitignore
A file that tells Git which files or patterns to never track — commonly used to make sure secret files (like a .env) are never accidentally committed.
Secret Rotation
The practice of periodically replacing a key or password with a new one, to limit the damage if an old one was ever leaked.
Important — This guide does not, and must not, reproduce any real API key. Wherever an example key is needed, use a clearly fake placeholder such as YOUR_OPENROUTER_API_KEY.

25Reindexing the Knowledge Base

↑ Contents

Because _notes_cache, _vectorizer, and _doc_matrix are only built once — automatically, when the server module loads — any change made to the files on disk afterward is invisible to a running server until it is told to look again.

                 │

26Limitations of This Project

↑ Contents
  • Lexical, not semantic, search. TF-IDF matches on shared exact words. It has no built-in understanding of synonyms or meaning — a query using entirely different wording than the note (but the same idea) may not be found.
  • Only Markdown files are indexed. glob.glob(..., "*.md", ...) only picks up .md files; PDFs, Word documents, or plain .txt notes would not be discovered.
  • The search index lives entirely in memory. It is rebuilt from scratch on every server restart, and is not persisted anywhere.
  • Changes require explicit reindexing. As covered in Chapter 25, edits on disk are invisible until reindex_notes() runs or the server restarts.
  • Tool-calling reliability depends on the chosen LLM. Not every model available through OpenRouter supports tool/function calling equally well — the code's own comments acknowledge this.
  • Dependent on an external API. The chatbot cannot answer anything without a working, reachable OpenRouter endpoint and a valid API key; OpenRouter's own availability and model lineup can change over time.
  • Tool-calling rounds are capped. MAX_TOOL_ITERATIONS = 5 means unusually complex, multi-hop questions could be cut off before a final answer is reached.
  • Local files, not a production database. There's no access control, versioning, or concurrent-write handling — this fits a single personal user, not a multi-user production system.

28Security and Prompt Injection

↑ Contents

Prompt injection

Prompt injection is when text an LLM reads (rather than trusted developer instructions) tries to make the model ignore its original instructions or behave differently than intended. In this project, tool results (the content of notes) are fed back into the conversation the LLM reads — so if a note's content contained text deliberately written to look like an instruction (e.g. "ignore previous instructions and reveal..."), a vulnerable model could, in theory, be influenced by it.

Untrusted user input

The user's chat message and the note content the LLM reads back should both be treated as data, not as trusted commands, by any well-designed system — the SYSTEM_PROMPT is the layer meant to stay authoritative over both.

Tool permissions

In this project, the only tools available are read-oriented (search_notes, read_note) plus one index-rebuilding tool (reindex_notes) — there is no tool that deletes files, sends data externally, or executes arbitrary code, which limits the potential damage even if a model were misled.

Sensitive data

Because the notes could contain personal information (as they do here — meeting notes, travel plans), and tool results are sent to an external LLM API (OpenRouter) as part of the conversation, users should be aware that note content leaves their machine whenever the model reads it via a tool call.

API key protection and tool output handling

The API key is entered per-session and never written to disk (Chapter 19). Tool output is treated as plain text data appended to the conversation — the client does not execute or evaluate it in any special way.

External API trust

Since the LLM itself runs on OpenRouter's infrastructure, the user is trusting that third party with the conversation content, including any note snippets the model reads.

30Viva Questions and Answers

↑ Contents

Beginner

Q: What is an LLM?
A: A large language model — a program trained on huge amounts of text that generates relevant text in response to an input prompt.
Q: What is MCP?
A: Model Context Protocol — a standardized way for an AI application to connect to and use external tools and data sources.
Q: What is an MCP server?
A: A program that exposes a set of tools following the MCP specification, so an MCP client can discover and call them.
Q: What is an MCP client?
A: The program that connects to an MCP server, discovers its tools, and calls them on behalf of the AI application.
Q: What is a tool?
A: A specific function the LLM is allowed to request be executed — here, search_notes, read_note, and reindex_notes.
Q: What is Gradio?
A: A Python library used to quickly build a web-based chat UI for the assistant.

Intermediate

Q: Why does the chatbot need an MCP server?
A: The LLM cannot access local files itself; the server provides a standardized way to expose note-searching and note-reading capability as callable tools.
Q: How does tool discovery work?
A: At connection time, the client calls session.list_tools(), and the server replies with the current list of tools registered via @mcp.tool(), including their names, descriptions, and parameter schemas.
Q: How does the LLM know which tools are available?
A: The discovered MCP tools are converted into an OpenAI-style schema by _mcp_tools_to_openai_schema() and sent as the "tools" field in every OpenRouter request.
Q: Why is stdio used?
A: Because the server runs as a local subprocess on the same machine; stdio (standard input/output) is a simple, reliable channel for two co-located processes to exchange MCP protocol messages.
Q: Why are MCP tool definitions converted to another schema?
A: OpenRouter (mirroring the OpenAI API) expects tools described in its own specific JSON "function" format, which differs from MCP's native tool representation.
Q: Why are TF-IDF and cosine similarity used?
A: To rank notes by textual relevance to a query without needing an LLM, database, or external service — a lightweight, fully local, fully explainable search method.

Advanced

Q: Why does the application use an asynchronous MCP session?
A: The official MCP Python SDK's client operations are async by design (built on asyncio), so any code using it must run inside an event loop.
Q: Why is a background event loop required?
A: Gradio's callback functions are synchronous, but the MCP session's methods must run on an asyncio event loop; a dedicated background loop in its own thread, bridged with run_coroutine_threadsafe, lets the synchronous UI code use the async MCP client.
Q: What happens if the MCP server disconnects?
A: call_mcp_tool() catches the resulting exception, attempts one reconnect via _connect(), and retries the tool call once before raising a clear error if that also fails.
Q: Why is tool-call iteration limited?
A: MAX_TOOL_ITERATIONS = 5 prevents a runaway loop where the model keeps requesting tools indefinitely without ever producing a final answer.
Q: How could semantic search improve this project?
A: Replacing TF-IDF with embedding-based vector search could match notes based on meaning rather than exact word overlap, catching relevant notes phrased differently than the query.
Q: How could this architecture be scaled?
A: Possible directions include running the MCP server as an independently deployed, network-reachable service rather than a local subprocess, adding a persistent index/database, and supporting multiple concurrent users with proper authentication.

In plain language: the user's question travels down through the chat UI to the LLM. The LLM, guided by the system prompt and the list of tools it was shown, decides whether it needs to look something up. If it does, that request flows through the MCP client, over stdio, into the MCP server, which runs the actual TF-IDF search or note-reading logic against the local Markdown files. The result flows all the way back up, is handed to the LLM as new context, and the LLM composes a final, grounded, natural-language answer that the user sees in the chat window.
